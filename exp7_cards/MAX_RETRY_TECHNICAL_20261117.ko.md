# 실험 7: 전송 간격 제한 없는 재시도 기술 시험

기존 본수집과 분리된 기술 대화다. **요청 간격을 인위적으로 늦추지 않고**
동시 대화 28개로 시작하며, 한 대화가 끝나면 사전 배정한 다음 독립 대화를
넣는다. 총 56개 기술 대화와 각 34턴을 배정한다. 이 선택은 모델당 평균
4개 동시 대화이며, 서비스의 물리적 최대 동시성이라는 뜻은 아니다.

각 대화는 독립된 CLI app-server 프로세스·thread 하나에서 10라운드와
마지막 네 질문까지 진행한다. 서버가 **실패로 확정해 반환한 429 또는 일부
일시적 5xx**만 같은 세션에서 즉시 재시도한다. 전송 속도를 낮추거나
클라이언트에서 추가 대기하지 않는다. CLI와 서비스 자체에 내장된 재시도와
지연은 별도로 있을 수 있다.

실패한 질문이 맥락에 두 번 남지 않도록, 실패 턴을 `thread/revert`로
제거하고 남은 thread의 이전 성공 턴 ID 전체가 정확히 일치하는지 확인한 후
다시 전송한다. 원본 실패·rollback·재시도 RPC는 별도 파일에 보존한다.
응답이 불확실한 전송, 세션 변경, 복구되지 않은 history, 도구 호출, 압축,
인증 오류 등은 429로 바꾸어 처리하지 않는다. 한 턴의 시도는 총 20회로
제한하며, 이를 모두 소진하면 해당 대화를 실패로 기록한다. 다른 대화는
독립적으로 계속 진행한다. 이 상한은 무한 재시도를 막기 위한 시도 횟수이지
초당·분당 전송 상한이 아니다.

결과는 성공한 턴/분, 완료 대화/시간, 실제 app-server `turn/start` 시도,
RPC 표면의 429, native 429 기록, 롤백 기록, 중단·실패, 컨텍스트 압축,
도구 이벤트, 같은 세션·프로세스 및 원본 감사로 구분한다. CLI 내부의 HTTP
재시도 횟수는 `turn/start` 개수와 같다고 가정하지 않는다. 압축·재시도 등
문제가 없었던 대화와 재시도한 대화는 구분해 보관하며, 이번 시험 자체는
어느 경우에도 본 실험 표본에 포함하지 않는다.

실제 provider를 쓰기 전, 로컬 가짜 서비스와 실제 CLI로 429를 강제로 발생시켜
첫 질문 및 이전 성공 턴이 있는 질문에서 같은 thread의 rollback·재시도와
중복되지 않은 입력을 검증한다. 여러 독립 34턴 대화와 동시에 발생한 429를
모의하고 결과를 감사한다. 불확실한 재전송을 자동으로 수행하지 않으며 기존
과학 실행의 STOP·freeze·원본을 변경하지 않는다.
