# v4의 완료 후 HTTP 종료 오류와 STOP 보존

마지막 FIFO 점검의 30개 대화·1,020턴은 원본 RPC와 과학 프로토콜 감사가
모두 통과했다. 물리 HTTP 1,023회 중 capacity 429는 3회였고 모두 복구됐다.
전체 성공 속도는 96.8035턴/분, p95는 7.9427초였다.

마지막 `retry-30`의 34턴 완료 수신은 **17:09:48.432260 UTC**였다.
그 뒤 마지막 HTTP 요청(ticket 1023, logical ID 1020)의 프레임 종료를 읽는 중
**17:09:48.514260 UTC**에 `RemoteProtocolError`가 발생해 보수적인 STOP이 기록됐다.
모델 응답·usage·동일 thread/PID는 이미 원본에 완결돼 있었지만,
기존 중계기는 이 뒤의 HTTP 종료 오류를 구분하지 않았다.

**v4 운영 게이트는 실패한 상태 그대로 보존한다.** summary, STOP, HALT,
원본 로그와 비공개 백업을 수정하지 않고, 새로운 모델 요청이나 대체 시행을
실행하지 않는다. 원본 백업 commit은 `dc7f5e00150eb67fb51f6da1964385aaad08007a`다.
후속 판단은 별도 `FIFO_POST_COMPLETION_REVIEW.json`에 기록한다.

## 앞으로의 코드 수정

완전한 `response.completed` SSE 프레임(status completed, id와 usage 포함)을
이미 전달한 뒤 **그 이후의 HTTP 프레임 종료만** `RemoteProtocolError`로 끝나면,
종료 진단을 기록하고 요청은 다시 보내지 않는다. 같은 응답을 유효한 chunked
종료로 마무리한다. 모델 답변이나 사용자 질문은 추가·수정하지 않는다.

완결 프레임 이전의 끊김·부분 응답은 기존처럼 불확실 상태로 STOP한다.
이 구분을 가짜 서버와 실제 CLI로 오프라인 검증한다. 추가 실모델 호출은 0회다.
이미 남은 v4 STOP을 자동 해제하거나 운영 게이트를 통과한 것으로 바꾸지 않는다.
새 수정 소스는 별도 본수집 프로필에 동결하고 readiness를 확인해야 한다.

병렬 수는 6을 유지한다. FIFO 10/100은 이전 6/100보다 약 2.59% 빨랐지만
미리 정한 5% 기준을 넘지 못했고 운영 STOP도 남았다. FIFO는 순서 역전 방지를
위한 수정으로 채택한다. 6/FIFO와 종료 처리 수정본의 실모델 처리량을
이번 자료에서 직접 측정했다고 표현하지 않는다.
