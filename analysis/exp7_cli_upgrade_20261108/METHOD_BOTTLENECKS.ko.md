# 실험 구조에서 확인한 병목

## 전체 서버 처리량과 현재 접속 조건을 구별해야 한다

지금의 429는 이 계정·모델·접속 경로의 요청이 거절됐다는 관측이다.
GPT 전체 서버가 몇 개 대화만 처리할 수 있다는 뜻이 아니다. 공식 paid API는
조직·프로젝트·모델 또는 공유 모델군별 RPM/TPM을 설명한다. 그 표의 높은
수치를 현재 ChatGPT 로그인 Codex나 구독 OAuth에 그대로 적용할 수도 없다.

현재 generic RPC 429에는 정확한 제한 종류·HTTP 본문·Retry-After 원문이 없다.
주간 사용량이 남아 있어도 단기 요청량, 토큰량, 모델 수용량 및 다른 제한은
가능하다. Cloud 프록시가 있는 사실만으로 프록시가 원인이라고 확정할 수 없다.
0.169.0-alpha.3 소스에서도 generic HTTP 429는 제한 종류를 자세히 구분하지
못하는 RetryLimit 경로로 매핑된다.

## 요청 입장 간격의 명시적 상한

현재 transport의 `_pace()`는 **worker마다 1초 간격**을 적용한다.
worker 하나가 모델 하나를 맡는 설계에서, pool을 3에서 10으로 올려도
그 worker는 이론상 분당 60턴보다 많이 시작할 수 없다. 프로세스 시작도
같은 pacer를 사용하므로 실제 턴 상한은 더 낮아질 수 있다.

8개 모델에 worker를 하나씩 두면 합계 이론상 최대 480턴/분이다.
원래 설계의 **77,856대화 × 34턴 = 2,647,104턴**을 이 속도로 계속 처리해도
**약 3.83일**이다. 실패·중단·초기화·백업·마지막 느린 모델의 대기 시간을
포함하지 않은 낙관적인 하한이다. 3일 완료에 평균 612.76턴/분,
2일 완료에 919.13턴/분이 필요하다. 처리 가능 시간 80%를 가정하면
각각 약 766턴/분과 1,149턴/분을 감당할 입장·응답 용량이 필요하다.

총합만 맞아도 충분한 것은 아니다. 모델마다 배정이 9,732대화/330,888턴으로
같으므로, 3일 목표에는 **각 모델에서 평균 76.59턴/분**, 2일에는 114.89턴/분이
필요하다. 빠른 모델이 먼저 끝나고 느린 모델만 남는 시간을 고려해야 한다.

따라서 전체 표본을 유지한 2~3일 목표에는 **입장 간격 변경과 그 부하를
실제로 처리할 수 있는 서비스 용량**이 함께 필요하다. 예를 들어 모델별
0.6초는 8worker 합계 이론상 800회/분이지만, 현재 계정에서 이 부하가
허용된다는 뜻은 아니다. 분산 VM마다 limiter를 따로 두는 것은 계정 공통
limiter를 구현한 것이 아니므로, 총 입장 예산을 나눠 관리해야 한다.

## 원래 실험 5보다 작업량이 훨씬 크다

실험 5는 보존된 성공 호출 83,160회, 약 10시간 56분 동안 분당 약 127회였다.
새 전체 계획의 턴 수는 약 31.83배이다. 실험 5의 속도를 그대로 유지해도
전체 계획에 약 **14.5일**이 걸린다. 최신 CLI가 조금 빨라지는 것만으로
같은 전체 표본을 2~3일에 마칠 수는 없다.

현재 persistent 방식은 이미 한 대화의 34턴에서 프로세스와 thread를
유지한다. 매 턴 exec/resume을 새로 실행하던 초기화 병목은 줄인 상태다.
두 번의 선택과 중간 피드백에 다음 질문이 의존하므로, 한 대화의 34턴을
모두 서로 독립적인 요청처럼 한꺼번에 병렬 전송할 수 없다.

## 로컬 저장소와 긴 지연

최신판 첫 실서버 점검에서 로컬 SQLite 초기화가 실패했다. 서버 429와
다른 문제이며, 기존 native home에 서로 다른 버전의 state/history migration이
적용되는 것이 확인됐다. 인증 home은 보존하고, 새 기술점검은 지원되는
`CODEX_SQLITE_HOME`을 자식에게만 지정해 DB를 분리한다. 본수집에 적용한다면
VM/버전/작업별 DB와 먼저 한 번 수행하는 직렬 초기화를 새 프로필에 기록해야 한다.

현재 디스크 fsync 200회 점검은 평균 약 0.32ms, p95 약 0.50ms였다.
OOM 기록은 0이었고 관측한 부하에서 CPU 포화 증거는 없었다. 이런 수치는
현재 점검 부하의 근거이며 80병렬까지 검증했다는 뜻은 아니다.

일부 응답의 긴 지연은 p95만으로 잘 드러나지 않는다. 안정판 반복 점검에서는
최대 약 43초인 응답이 있어 p95 약 5.26초와 달리 대화 4개의 전체 완료 속도가
50.4턴/분으로 떨어졌다. 평균 처리량, 완료 대화 수, p99·최대 지연과
마지막 느린 대화가 끝날 때까지 걸리는 시간도 함께 봐야 한다.

## 오류 후 전체 중단의 영향

실험 5와 비교하면 현재는 generic response 429 하나도 전체 STOP을 만들고
다른 진행 중인 대화가 중단될 수 있다. 이 정책은 불확실한 요청을 지키지만,
순간 오류가 자주 나면 생산적인 전체 수집 속도는 짧은 성공 구간보다 훨씬 낮다.
모델별 수용량 오류인지 계정 공통 오류인지 명확히 확인할 수 있다면,
영향을 받은 작업만 멈추고 다른 작업을 진행하는 정책을 별도로 검토할 수 있다.
generic 429만으로 제한을 모델별이라고 가정하여 계속 돌려서는 안 된다.
실패 시행을 성공 시행으로 임의 대체하거나 새 STOP을 자동 해제하지 않는다.

## 다음에 검증할 수 있는 방법

- 최신 안정판 + 분리된 DB: 일관된 새 실행 환경을 만들 수 있다.
  속도 이득은 별도 실제 비교 결과로 판단한다.
- 모델 분산과 총 입장 제어: 두 모델의 짧은 점검에서 나온 수치를 모든
  모델의 고정 최대 병렬 수로 일반화하지 않고, 모델별/계정별 부하를 함께 측정한다.
- 공식 구독 OAuth → 공개 Responses API: 별도 연동 로그인이 필요하다.
  paid API 키 없이 가능한 공식 경로이지만 같은 구독의 제한은 적용된다.
  직접 클라이언트는 도구 설명을 제거하고 HTTP 오류를 더 정확히 보존할 수 있다.
- paid API: 실제 모델 접근권, 해당 계정의 RPM/TPM과 예산을 확인하면
  더 높은 처리량을 계획할 수 있다. 현재 환경에 API 키가 없으므로 실측하지 않았다.
- 단계별 표본 수집: 기존 설계 자체를 줄이는 대안이므로 별도 설계 결정이 필요하다.
  이 조사에서 조건·모델·effort·표본 수를 변경하지 않았다.
