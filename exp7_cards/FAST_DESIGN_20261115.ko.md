# 실험 7: 최대 성공 처리량을 찾는 속도 설계

**상태: 오프라인 프로토타입. 본수집을 자동 재개하지 않는다.** 사용자 목표는
50회/분 고정이 아니라 실제로 성공하는 요청의 처리량을 가능한 높게 만드는 것이다.
기존 실행과 freeze·STOP·원본을 수정하지 않는다.

## 기존 실행에서 확인한 사실

- 기술 점검 21개 중 20개가 34턴을 완주했다. 5.6 Sol/high의 32턴에서는
  협업 도구 호출과 하위 에이전트 이벤트가 실제 감지되어 해당 점검이 실패했다.
  도구 사용을 허용한 관측으로 바꾸거나 성공으로 재분류하지 않는다.
- 본수집은 완주 0개, 중단 6개다. 여섯 대화의 미완료 요청은 각각 원본 상태와
  journal에 남겼다. 그 외 8,394개 배정은 현황판에 미시작·미보고로 나타난다.
  이전에 실제 시작된 대화를 자동 재생하거나 암묵적으로 대체하지 않는다.
- 여러 worker가 독립 Git 캐시로 한 현황판을 동시에 갱신하면서 세 worker에서
  `Concurrent board updates prevented confirmation`이 발생했다. 이후 각 중단
  상태와 공개 결과 참조를 현황판에 조정해 반영했다.
- 기술 점검의 성공 711호출은 최초 시작부터 마지막 응답까지 약 26.75분,
  약 26.6회/분이었다. 이 값은 이전 100회/분 부하 시험과 다른 구성이고,
  중단·조정 오버헤드가 포함된 해당 실행의 관측치다.
- 이전 성공 시험은 100회/분 송신 상한에서 실제 83.7회/분, 110회/분 단계는
  약 97.3회/분 관측 뒤 429가 있었다. 실험 5의 이전 전체 평균은 127회/분이었다.
  어느 수치도 현재 환경의 영구 한도는 아니다.

## 개선된 전송·현황판 구조

1. **잠금 분리.** 실제 `turn/start`를 app-server로 보내는 직전에만 공통 요청
   간격을 적용한다. GitHub 현황판 조회는 이 잠금 바깥에서 진행한다. 공통
   상태 확인은 대기 중 주기적으로 갱신하고, 최종 쓰기 직전에는 로컬 중단
   플래그를 다시 확인한다. 중단 요청의 원격 전파는 기존 polling 지연 한계가 있다.
2. **현황판 쓰기 직렬화.** 한 VM의 7개 worker는 공통 파일 잠금으로 GitHub
   현황판 변경을 직렬화한다. 모델 호출과 분리된 잠금이므로 하나의 현황판
   업로드가 모든 실제 모델 전송을 잠그지 않는다. 이 방식은 다른 VM에 걸친
   분산 잠금이 아니며, 다중 VM 실행에는 별도 전역 조정이 필요하다.
3. **측정 기반 증속.** 별도 기술 대화만으로 100회/분 상한에서 시작해 성공
   턴, 실제 성공 처리량, 지연·미확정 요청과 RPC/native 429를 측정한다.
   각 단계는 최소 150개 성공 요청과 90초의 관측을 갖는다. 관측 처리량이
   상한의 85% 미만이면 동시 대화 수를 7개씩 늘려 공급을 채우고, 그렇지 않으면
   요청 상한을 분당 10회씩 올린다. 7개 모델 × 모델당 10대화의 70개는 기존
   worker 설계상 기술 점검의 최대 후보이지 검증된 서비스 용량이 아니다.
   인접한 깨끗한 단계의 성공 처리량이 3% 미만으로 개선되면 우선 더 높은
   관측값을 보인 설정에서 재측정한다. 반복 측정 전에는 확정 최대라고 부르지 않는다.
4. **실패 처리.** 429, native 429 재시도, 미확정 요청, 도구 호출 또는 누락된
   429 텔레메트리가 있으면 단계 상승을 중지한다. 이미 전송했을 수 있는 요청은
   재전송하지 않는다. 마지막 깨끗한 단계는 다음 설계를 위한 참고값이며,
   실패한 단계의 대화를 본수집에 넣지 않는다.

`fast_pacing.py`는 실제 전송 지점에 쓰는 VM 공통 pacer와 기술 단계 결정 규칙,
`fast_coordination.py`는 VM 공통 현황판 쓰기 잠금이다. `fast_transport.py`는
실제 CLI app-server를 사용하면서 `turn/start` 쓰기를 pacing하는 별도 어댑터다.
기존 어댑터·프로토콜과 구별되는 새 freeze에 결합해야 하며, 아직 기존 운영
worker에 연결하거나 실험을 시작하도록 허용하지 않았다. 단계 결정 함수는
구현됐지만 기술 부하 측정의 자동 실행과 단계별 새 프로파일 적용은 아직
연결되지 않았다. 동시성과 요청 상한의 증가는 실제 부하 시험으로 확인해야 한다.

## 오프라인 검증과 남은 실행 차단

- 로컬 Git 서버에서 7개 프로세스가 동시에 모델 소유권을 선점하고 현황판을
  갱신하는 검사를 통과했다. 다중 VM·실제 GitHub 장시간 부하는 검증되지 않았다.
- 독립 CLI 두 대화의 요청이 모의 서비스에서 실제로 겹쳤고, 별도의 34턴 모의
  대화는 기존 원본 RPC 감사·세션 일관성 검사를 통과했다.
- 로컬 인위적 지연 실험은 병목을 재현하는 단위 점검이지 실제 모델 호출의
  처리량 시험이 아니다. 속도 상한이나 요금을 여기서 추정하지 않는다.
- 더 중요한 문제: 현재 CLI는 `features.multi_agent=false` 등 기존의 비활성화
  설정, 세션 관련 환경 변수 제거, `dynamicTools=null`, 실험 API 비활성화
  조합을 시험해도 모델 측 warmup에 협업·함수 도구 9개를 노출했다.
  실제 5.6 Sol/high 기술 대화에서도 협업 도구 이벤트가 발생했다.
  `tool_surface_probe.py`는 로컬 가짜 서비스로 이 문제를 재현하고 도구가
  하나라도 있으면 실패 상태를 돌려준다. 과학 시행에서 모델이 도구를 사용한
  경우를 조용히 성공 처리하지 않는다.

따라서 속도 설계와 오프라인 전송/동시성 점검은 완료됐지만, **도구 비노출을
입증하지 못해 실제 가속 기술 부하 시험과 본수집 재개는 하지 않았다.** 다음
실행 전 별도 프로파일에서 도구 노출/사용을 차단하거나 그 영향을 명시적으로
검증해야 한다. 새 속도 프로파일, 요청 상한과 배정은 기존 freeze와 분리해서
고정하고, 백업 및 중단된 6개 대화를 조정한 다음 별도 실행으로 시작한다.
