# 실험 5와 7의 실제 속도 비교

2026-11-07. 모델 호출 없이 기존 기록과 Astra VM의 평가 상태만 비교했다. 이 문서는 운영 분석이며 실험 결과의 원자료나 사전 동결된 실험 코드를 변경하지 않는다.

실험 5 수치는 2026-10-12 17:38:31 UTC 준비 완료부터 10-13 04:34:43 최종 평가 완료까지 약 10시간 56분 기준, 중단·재시작을 포함한 전체 경과시간 계산이다. 15개 용량 실패가 기록됐고, 당시 사용자의 명시 지시로 미완료 대화를 새로 대체했다. 현재 실험 7은 다수 VM의 합계가 아니라 Astra VM 한 대의 지속 부하 구간이며, 서로 다른 모델 혼합·시간대·조건·실패 정책을 포함하므로 인과적인 성능 비교가 아니다.

같은 Astra 모델의 실험 5 완료 대화 360개와 11,880개 정상 호출을 원본 압축 아카이브에서 읽으면 호출당 평균 16.91초, 호출 중앙값 18.39초, 대화 완료 시간 중앙값 565.6초다. 현재 Astra 7번 작업의 1,017개 호출은 평균 3.81초였고, 17:03 UTC 현재 전체 완료 대화 중앙값은 133.9초였다. 현재가 호출별로 느려진 것은 아니다. 과거의 서버 부하·CLI·조건 구성과 시간대가 다르므로 특정 원인을 단정할 수 없다.

본실험은 대화 수가 실험 5의 30.9배이고 대화당 호출도 33에서 34로 증가해 총 호출이 약 31.8배다. 여기에 이번 VM의 3병렬과 공통 STOP으로 인한 중단이 경과시간에 영향을 준다. 현재 8개 VM이 모두 일하고 있는 것은 아니다: 17:17 UTC 현황판에서 Astra가 실제 작업 중이었고 다른 소유 모델은 미시작 또는 blocked 상태였다. 예약 숫자와 실제 동시 요청 수는 다르며, 다른 VM의 소유권을 자동으로 뺏지 않는다.

## 실행 가능한 개선 순서

1. 이미 준비된 다른 VM을 각 모델별로 재개한다. 기존 소유권·원시 로그를 확인하고 미시작 배정만 이어간다. 공통 quota 여부는 미확인이고, stale 소유권이나 글로벌 STOP을 무단 해제하지 않는다. 현재 사용자가 요청한 대로 별도 기술점검 모델 호출은 하지 않는다.
2. 현행 3병렬은 유지한다. 10병렬 두 시도는 각각 응답 100개 성공 후 CLI의 모델 목록 갱신에서 실제 429가 관측되어 중단됐다. 이 결과는 생성 모델 자체의 상한을 식별하지 못하지만, 같은 방식으로 10을 계속 밀어붙이는 것은 반복 중단을 초래했다. 4~9의 지속 가능성은 아직 관측하지 못했다.
3. 개선 후보로 장시간 유지되는 Codex app-server를 별도 운영 구현으로 준비해 호출마다 새 CLI를 만드는 부담과 모델 목록 조회를 줄일 수 있는지 확인한다. 실험 프롬프트, 모델, 추론 수준, 스키마, 대화 기록 및 에러 감지가 동일해야 하며 동결된 수집 코드를 실시간으로 바꾸지 않는다. 오프라인 구현은 새 모델 호출 없이 가능하지만 실제 속도 향상과 응답 동등성은 사후에 별도 검증해야 하므로 현재 보장하지 않는다.
4. 오류의 영향 범위를 판별할 수 있을 때 해당 모델만 멈추고 나머지 모델은 계속하도록 조정 정책을 개선한다. 인증·공유 quota·오류 범위가 불명확할 때는 현재 공통 STOP을 유지한다. 모델별 중단이 안전하다는 근거 없이 전역 STOP을 무시하지 않는다.

단순 산술로 8대가 각각 현재 Astra 수준의 76대화/시간을 유지하면 전체는 약 608대화/시간, 77,856개는 약 128시간이다. 이는 모델 속도·자원 한도·중단이 서로 독립적이라는 가정의 예시이며, 실제 8 VM 속도가 아니다.
