# 실험 7의 capacity 429 재시도와 처리량 운영

2026-11-08 요청에 따른 새 운영 전략이다. 기존 수집분과 동결 실행 프로필은
보존한다. 이전 본실험과 기술점검의 STOP은 계속 유효하다.

## 판단 기준

429가 있어도 고정된 복구 규칙으로 전체 배정을 완결할 수 있다면 처리량을
측정할 수 있다. 성공 턴/분에는 요청 간격, 재시도 대기, 느린 응답, 마지막
남은 대화의 처리까지 포함한다. 중단 직전의 빠른 구간만으로 완료 시간을 추산하지 않는다.

선택한 병렬 수·물리 요청 시작 상한·검증 범위는
[기계 판독 실행 전략](../analysis/exp7_retry_efficiency_20261108/results/recommended_execution_profile.json),
근거는 [비교 보고서](../analysis/exp7_retry_efficiency_20261108/REPORT.ko.md)에 기록한다.
초당·분당 상한에는 **재시도를 포함한 모든 실제 HTTP 시도**가 들어간다.
pool 수와 요청 속도는 서로 다른 설정이다.

**해석 범위 보완(2026-11-08):** 6병렬/100회는 한 VM·두 모델에서 설정한
상한 아래 비교한 잠정값이다. 공급자의 고정 한도나 여러 VM의 최대 효율을
식별한 값이 아니다. 최근 약 94~97턴/분을 두 VM 합산으로 해석하지 않는다.
실제 이전 두 VM 동시 구간은 약 110턴/분이었다.
[실험 5와 측정 범위·전송 상한 재점검](EXP7_EXP5_THROUGHPUT_REASSESSMENT.ko.md)에
원본 검증과 계산을 남겼다. 기존 동결 프로필·수치·STOP은 변경하지 않았다.

검증한 구성에서는 개별 CLI transport의 로컬 시작 간격을 0으로 두고,
공통 HTTP 입장 제어기 한 곳에서 전체 속도를 제한했다. 여기에 기존의
모델별 1초 간격을 별도로 더하면 서로 다른 실행 전략이 된다.
이 설정도 새 동결 실행 프로필에 명시해야 한다.

## 같은 논리 턴의 복구

공유 입장 대기줄은 선착순 FIFO로 처리한다. 요청 간격만 제한하고 순서를
보장하지 않으면 뒤에 온 작업이 먼저 전송돼 일부 대화가 오래 기다릴 수 있다.
입장 대기, 실제 HTTP 왕복, 전체 논리 턴 지연을 구별해서 측정한다.

예를 들어 5라운드 질문을 제출한 뒤 공식 서버가 응답 시작 전
`429 / rate_limit_error / turn_rate_limit_exceeded / Retry-After: 22`를 반환하면,
모든 작업의 새 전송을 서버가 지정한 시간과 짧은 jitter만큼 대기시킨다.
그다음 원래 요청 바이트를 그대로 다시 전송한다. CLI에는 새 질문이나
`turn/start`를 추가하지 않는다. 모델이 보는 대화에 “다시 해봐” 같은 문장을 넣지 않는다.

구현은 [exp7_retry_transport.py](../scripts/exp7_retry_transport.py)에 있다.
요청 본문은 CLI가 압축한 경우에도 해석·수정·재압축하지 않는다.
기존 native 인증·프록시·CA와 공식 endpoint를 유지하고,
한 시행에서 app-server 프로세스와 thread를 유지한다.

허용되는 복구는 **완결된 명시적 capacity 429**에 한정한다. 한 논리 요청의
429 재시도는 최대 4회이고, 다음 대기까지 합산한 경과가 240초를 넘으면
추가 복구를 예약하지 않는다. CLI 논리 턴 timeout은 360초다.
native request/stream 재시도는 0으로 고정해 다른 오류의 숨은 재전송을 막는다.

HTTP 200의 완결 프레임 이전 스트림 오류·연결 단절·시간 초과, 인증·quota·알 수 없는 오류는
완료 여부가 불확실하거나 다른 조치가 필요하므로 STOP과 원본을 보존한다.
재시도 예산이 끝나면 실패·중단 상태를 남긴다. 다른 응답으로 대체하거나
새 대화에서 같은 시행을 다시 실행하지 않는다. 기록된 STOP을 자동 해제하지 않는다.

완전한 `response.completed` 프레임(status completed, id와 usage 포함)을 이미
전달한 뒤 HTTP 프레임 종료만 `RemoteProtocolError`로 끝난 경우에는 종료
진단을 기록하고 요청을 다시 보내지 않는다. 이 마지막 처리는 실제 CLI와
가짜 서버로 검증했다. 이미 기록된 v4 STOP은 그대로 남아 있다.

## 여러 VM

권장 파일의 `global_pool`과 `physical_starts_per_minute_global`은 계정 전체에
적용할 예산이다. 각 VM에 같은 전체 값을 반복해서 주면 합계가 커진다.
현재 기술점검은 **한 VM에서 두 모델이 같은 입장 제어기와 cooldown을 공유**한다.
여러 물리 VM에서의 효율을 측정한 결과로 해석하지 않는다.

여러 VM의 새 프로필을 만들 때는 실제 pool의 합계와 예약 합계를 맞추고,
계정 예산을 공통으로 제어하거나 서로 겹치지 않는 속도 예산으로 나눠야 한다.
재시도도 각 예산을 소비해야 한다. 작업 선점·소유권·원본 저장은 공통 조정
기록으로 검증하며, 모든 VM이 독립적으로 전체 실험을 생성하지 않게 한다.
현재 코드의 loopback 중계기는 해당 VM 안에서 공유하는 구성이다.

## 새 본수집에 적용할 때

이번 비교의 실행기는 [exp7_retry_efficiency_study.py](../scripts/exp7_retry_efficiency_study.py)이며
**별도 기술점검용**이다. 기존 worker와 readiness가 새 전송 정책을 자동으로
사용하는 것은 아니다. 권장 전략을 본수집에 반영할 때는 새 실행 ID·freeze와
정확한 source/CLI/config를 만들고, 원래의 전체 배정과 대응표를 유지한다.
언어·프롬프트·스키마·질문 순서·목표 설정·표본 수는 운영 최적화 때문에 바꾸지 않는다.

HTTP/SSE를 사용한 이 프로필은 기존 WebSocket 수집분과 구별한다.
응답 분포 동등성을 증명한 것은 아니므로, 이전 수집분과 새 본실험의 주 분석을
합치지 않는다. 모델·effort별 readiness와 원본 감사를 새 프로필에 맞게 확인해야 한다.

원본 감사는 매 대화의 34개 논리 턴, 동일 프로세스/thread, 각 턴의 한 번의
질문 제출, 모델·effort·프롬프트·스키마·도구 사용 여부를 검사한다.
별도 HTTP 감사는 재전송이 명시적 429 직후에만 있었는지, 요청 바이트가
같은지, 공통 cooldown을 지켰는지 검사한다. 모든 시도·실패·미확정 상태와
백업 해시를 남긴다. 공급자 내부에서 모델이 실행된 횟수의 완전한 증명은 아니다.
