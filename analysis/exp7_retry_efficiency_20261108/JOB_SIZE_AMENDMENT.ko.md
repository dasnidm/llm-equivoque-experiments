# 실제 작업 크기와 pool 소진 구간의 추가 검증

초기 v2의 6·8병렬 결과를 확인하는 중, 12대화 고정 배치가 pool 선택에
큰 영향을 준다는 점을 확인했다. 6병렬은 처음 6개가 약 125~139초에 끝나고
다음 6개로 채워진다. 8병렬은 처음 8개가 약 141~177초에 끝난 뒤,
남은 4개가 최종 약 277초까지 이어졌다. 전체 처리량과 공통 60~180초 구간의
순위가 달랐다. 이 추가 시간 구간은 원래 계획에 없던 보조 진단이다.

본수집 manifest의 작업 크기를 확인하니 **2,592작업은 30대화, 8작업은 12대화**다.
12대화 배치만으로 본수집의 pool을 정하면 대표성이 부족하다.
초기 자료와 원래 결정은 그대로 보존하며, 실제 크기에 더 가까운 별도 검증을 추가한다.
본수집의 조건·배정·표본 수를 변경하는 것은 아니다.

## 새 기술점검 v3

- 실행 범위 `equivoque-2026-11-08-exp7-retry-efficiency-v3-job30`.
- `/workspace/work/exp7-retry-efficiency-20261108-v3-job30`에 새 프로필·배정·상태를 저장한다.
- 기존 v2의 세 비교와 원래 조건부 확인 실행은 그대로 완료·보존한다.
- baseline은 6병렬·분당 100회 시작 상한이다.
- 후보의 pool은 v2의 8/110, 10/160 중 공통 60~180초 구간 성공 턴/분이
  더 높은 쪽으로 고른다. 수치가 같으면 더 낮은 pool을 사용한다.
  실제 v2에서 해당 수치는 8병렬 99.0, 10병렬 100.0이었다.
  **새 후보의 물리 시작 상한은 baseline과 같은 분당 100회로 맞춘다.**
  따라서 v3는 **6/100 대 10/100**이다. pool 확대 효과를 시작 속도와 분리하고,
  초기 10/160에서 보인 긴 cooldown을 줄이는 평활화 전략을 검증한다.
  v2에서 두 후보 모두 12개 대화는 완결했지만 전체 속도 이득은 없었다.
- 두 설정에 각각 새 **30대화(두 모델 각 15개) × 34턴 = 1,020 논리 턴**을 배정한다.
  원래 두 frozen 시작 설정·언어·프롬프트·스키마·effort·질문 순서를 유지한다.
  한 모델의 실제 30개 trial을 그대로 재생하는 것은 아니며, 계정을 공유하는
  두 모델의 작업량을 30개로 맞춘 운영 비교다.
- source의 변경은 물리 시도 예산을 명시적으로 전달하는 인자 추가다.
  한 설정의 물리 예산은 1,320회, 새 전송 입장 마감은 900초다.
  429 재시도·동일 요청 바이트·공통 cooldown·미확정 요청 중지 정책은 v2와 같다.
- 순서는 baseline → 최소 65초 무호출 → 후보이며, 이전과 같은 별도 원본 감사와
  비공개 백업·원격 해시 검증을 한다. 실패 시행은 대체하지 않는다.

두 설정 모두 30개 대화가 완결·감사 통과하고, 후보의 전체 성공 턴/분이
baseline보다 5% 이상 높으며 보조 공통 구간 속도도 baseline 이상이면
해당 설정을 새 실행 전략으로 선택한다. 그 외에는 6/100을 유지한다.
이 추가 검증의 최대 논리 요청 수는 2,040회다.

이는 초기 순위 불일치와 실제 작업 크기 확인 후 정한 **적응적 운영 검증**이다.
처음부터 사전 등록된 확증 실험이라고 표현하지 않는다. 초기 v2와 별도 표로
보고하고, 모든 비교의 순차 실행·서버 상태 변동·두 모델 medium 조건의 한계를 기록한다.
어떤 결과든 새 본실험의 과학적 표본에는 포함하지 않는다.
