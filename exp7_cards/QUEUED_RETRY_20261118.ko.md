# 실험 7: 프로세스 생존과 턴 재시도

**상태: 별도 프로토타입·검증용 기술 실행기. 기존 본수집 worker와 freeze는
변경하지 않았고, 이 코드를 본수집에 아직 연결하지 않았다.**

## 처리 방식

- 한 시행은 하나의 CLI app-server 프로세스와 thread에서 10라운드와 마지막
  네 질문까지 34턴을 진행한다. 한 세션에서 동시에 두 턴을 보내지 않는다.
- **프로세스가 살아 있고 턴이 실패로 확정되면** 실패한 턴을 thread에서 제거하고,
  앞서 성공한 턴 ID 전체를 대조한다. 일치하면 같은 프로세스·thread의 해당
  요청을 공통 FIFO 전송 대기열 뒤에 넣는다. 재시도 횟수 상한과 추가 대기,
  분당 전송 상한은 없다. 대기열은 로컬 전송 진입 순서를 정하며, 모델 응답을
  기다리는 동안 다른 대화의 전송을 잠그지 않는다. OS 스케줄링에 따른 실제
  pipe 쓰기 순서까지 엄격하게 보장하는 것은 아니다.
- 실제 실패와 rollback 원본 RPC를 각 시도마다 디스크에 기록·동기화한다.
  무제한 실패가 이어지는 동안 재시도 목록을 메모리에 무한히 쌓지 않는다.
  CLI stderr도 새로 추가된 부분만 읽어, 재시도가 많아질수록 전체 로그를
  반복해서 읽는 병목을 제거한다. 로그가 잘린 경우는 숨기지 않고 보류한다.
  성공 후에는 전체 재시도 저널을 사용해 원본 hash와 thread 이력을 감사한다.
- **프로세스가 실제 종료되면** 그 시행을 `failed / process_exited`로 남기고
  이전 응답과 미완료 요청을 보존한다. 같은 표본 ID로 프로세스를 다시
  시작하거나 미완료 턴을 자동 재전송하지 않는다. 프로세스가 애초 시작되지
  않았을 때는 `unstarted`로 분리한다.
- 응답 지연만으로 살아 있는 프로세스를 죽이거나 요청을 다시 보내지 않는다.
  타임아웃이 나도 같은 응답을 기다린다. 프로세스가 살아 있지만 전송 결과나
  rollback 이력이 확실하지 않거나, 도구 호출·압축 등으로 실험 기록이
  훼손된 경우는 `held`로 보존한다. 재전송은 하지 않으며 별도 확인이 필요하다.
  `held` 프로세스가 나중에 실제 종료되면 감시자가 실패 상태로 기록한다.
  컨트롤러를 잃어 프로세스 생존 여부 자체를 모를 때는 종료로 추정하지 않는다.
  기록 작업 오류나 예산 소진으로 프로세스가 살아 있는 경우에도 자동으로
  닫지 않고 `held`로 유지한다. 프로세스 상태 분류 전에 컨트롤러가 죽어
  남긴 미분류 실패 checkpoint도 종료로 단정하지 않는다.

한 Python 컨트롤러에서 관리하는 여러 대화가 FIFO admission 큐를 공유한다.
기존처럼 모델별로 **서로 다른 Python worker 프로세스**를 쓰는 운영 방식에선
메모리 큐가 자동 공유되지 않는다. 이를 본수집에 연결할 때는 단일 컨트롤러를
사용하거나 별도의 프로세스 간 큐를 검증해야 한다. 한 대화가 34턴을 진행하는
동안 하나의 대화 슬롯을 차지하므로, 모든 슬롯이 429 대기 중이면 더 많은
대화를 자동으로 생성하지 않는다. 큐와 동시 대화 수는 서로 다른 설정이다.

전송 전에는 호출자가 STOP 확인과 저장 공간 점검을 포함한 gate를 제공해야
한다. 저장 공간 부족, 관찰할 수 없는 전송 결과, 잘못된 이력 등을 무시하고
재전송하지 않는다. 사용자 요청에 따라 명시적 terminal 턴 오류는 오류 종류에
관계없이 재시도하므로 영구적 인증·설정 오류는 계속 대기할 수 있다. 이 경우
현황판에서 대기 원인을 확인해야 하며, 사용량과 디스크는 계속 늘 수 있다.
기술 실행기는 저장 공간 상태를 최대 1초 간격으로 갱신하며 전송 속도 자체에
고정 간격을 추가하지 않는다.

## 검증

실제 Codex CLI를 **로컬 모의 서버에만** 연결해 25회 연속 429 후 동일
프로세스·thread에서 34턴을 완료하고 전체 원본 RPC와 rollback을 감사했다.
중간 턴에서 429가 난 경우 이전 질문 순서가 유지되고 실패한 질문은 한 번만
추가되는지도 확인했다. 7개 독립 프로세스를 동시에 사용한 34턴 대화와
429 복구도 검사했다. 별도로 프로세스 사망, 20회 초과 실패, FIFO 대기자
사망, 응답 지연, 검증 실패 시 live hold, 컨트롤러 정보 유실, 저널 변조를
검사한다.

별도 실제 provider 기술 단계 `queue-live-20261118-a`에서는 일곱 모델의
7개 시행이 각각 동일 프로세스·thread에서 34턴을 완료했다. 238턴 성공,
429 실패 시도 130회가 모두 롤백 후 재시도로 복구됐고 7개 원본 기록 감사가
통과했다. 전체 평균 80.1 성공 턴/분, 압축·도구 이벤트는 0이었다. 이것은
7개 대화로 수행한 기술 시험이고 28개 동시 본수집의 속도 추정치가 아니다.
해당 단계는 원래 commit `a1643bc4a`로 수행됐다. 이후 추가한 컨트롤러
중단·예산·종료 경계 수정은 별도 회귀 검사와 새 단계로 확인한다.
