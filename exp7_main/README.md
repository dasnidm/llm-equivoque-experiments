다른 환경의 채팅에서 실행하는 방식이다. 이 환경의 worker가 다른 Cloud 환경을 직접 생성하거나 제어하지 않는다. 각 환경의 인증은 그 환경에서 수행하며 인증 파일을 Git에 넣거나 VM 간에 복사하지 않는다.

## 실행 단위와 예산

8모델 × low/medium/high × 카드/고양이에서 네 형식(영어/schema, 영어/자연어, 한국어/schema, 한국어/자연어)을 사용한다. obj/seq는 형식별120대화, KK/KD/DK/DD는 형식별30대화다. R_A는 영어/schema에서만 추가하며 obj32, 나머지 게임 각각30이다.

- obj120: A/B/C/D 목표별30대화. R_obj32: 목표별8대화.
- seq: 모든 조건에서 **A C B D B A D C A B**라는 새 공통 목표 목록을 사용한다. 이는 과거 실험5의 전체 목록을 재현한 것이 아니다.
- 각 대화는 새 세션으로 시작해10라운드와 후속4응답을 수행한다. 총34호출이다.
- 전체77,856대화, 게임778,560라운드, 완주 기준2,647,104평가 호출.
- 모델별9,732대화. 작업325개(324개×30대화＋마지막12대화), 전체2,600작업.
- 별도 기술 점검은 모델별18대화·최대612호출이다. 본실험에 합치지 않는다. 최초 전체 점검 상한은144대화·4,896호출이며 별도 접근 진단도 평가와 구분해 기록한다.

작업 안에는 여러 추론수준·게임·언어·프레임이 섞인다. 대상 모델의 선택은 자유이고, 실제 K/D 경로를 사전 배정하지 않는다. 핵심 조건마다 개발60/잠금 평가60이며 같은 대화의 라운드를 나눠 검증하지 않는다. [분석 계약](analysis_contract.json)은 관측 보고와 내부 기제의 차이, 결측과 평가 자료 사용 범위를 명시한다.

## CLI

Python, JSON 검증용 `jsonschema==4.26.0`, 동결 파일에 기록한 Codex CLI 버전을 사용한다. 저장소 최상위에서 실행한다. 모든 경로는 각 환경의 실제 checkout에 맞춘다.

```bash
codex --version
codex login status
gh auth status
python -m pip install -r exp7_main/requirements.txt
python -m exp7_main.worker verify --freeze manifests/equivoque-2026-11-07-exp7-main-v1/freeze.json
```

로그인 상태 표시만으로 실제 호출의 인증 성공이 보장되지는 않는다. 401이 발생하면 해당 환경에서 `codex login --device-auth`를 실행하고 사용자가 공식 인증 페이지에서 완료한다.

```bash
python -m exp7_main.worker prepare \
  --freeze manifests/equivoque-2026-11-07-exp7-main-v1/freeze.json \
  --work-dir /workspace/work/exp7-main-worker \
  --model auto --concurrency 1

python -m exp7_main.worker run \
  --freeze manifests/equivoque-2026-11-07-exp7-main-v1/freeze.json \
  --work-dir /workspace/work/exp7-main-worker \
  --model auto --concurrency 1
```

`run`은 해당 모델·동결 버전의 실제 기술 점검이 통과한 경우에만 진행한다. 기술 점검은 모든 추론수준·네 형식·R·여섯 게임·두 프레임을 포함하지만 전체 조합을 하나씩 검사한 것은 아니다. 독립적인 사람의 의미 검토가 완료됐다고 주장하지 않는다.

`prepare`와 `run`은 같은 지속 저장 디렉터리를 사용한다. 단순 재실행은 저장된 담당 모델과 원본을 확인하며 실패·미확정 모델 요청을 다시 보내지 않는다. VM 전체가 없어지거나 디스크가 유실됐을 때는 새 디렉터리로 기존 선점 작업을 가져가지 말고 먼저 상태를 조사한다. 장시간 실행은 환경에서 유지되는 백그라운드 프로세스로 띄우고 PID와 로그 경로를 기록한다.

## GitHub 작업 규칙

1. 공통 브랜치의 최신 작업판을 읽고 모델 하나를 원자적으로 선점한다.
2. 담당 모델의 다음 작업을 선점해 일반 fast-forward push를 수행한다.
3. 원격 담당자·토큰이 일치하는 것을 확인한 뒤에만 호출한다.
4. 작업이 끝나면 연구 자료를 모델별 결과 브랜치에 올리고 원격 파일을 확인한다.
5. 원본 해시·완료/실패/중단/미시작 수·호출 수·결과 커밋을 공통 작업판에 기록한다.
6. 다음 비어 있는 작업을 가져간다. 다른 환경이 맡은 모델은 자동으로 뺏지 않는다.

강제 push, 선점 충돌을 무시하는 rebase, 시간 초과만으로 선점 해제, 실패 대화 대체는 하지 않는다. Git 전송의 재확인은 모델 요청 재시도와 구분한다. 동결 소스를 바꿔서 검사를 우회하지 않는다.

처음 공통 동시성 상한은 **전체10**이다. 각 추가 환경은1개씩 예약하고 현재 시작 환경이최대3개를 예약하면8환경의 합은10이다. 이는 VM별10개·합계80개의 용량이 검증됐다는 뜻이 아니다. 증설은 별도 부하 확인과 예약 상한 변경 후 적용한다.

worker는 요청 전에 최대10초 캐시의 원격 권한·STOP을 확인한다. 이미 전송한 요청을 원격 STOP으로 즉시 취소할 수는 없다. 429 또는 영구적인 인증 실패 진단이 나오면 새 호출을 중단하고 공통 STOP을 기록한다. 네트워크가 끊겨 소유권을 확인할 수 없을 때도 호출을 계속하지 않는다.

## 저장과 공개

로컬에는 대화 상태, 요청 전후 기록, 원시 CLI 증거와 해시를 보존한다. GitHub에는 배정·선택·피드백·모델 답변·판독 결과·집계와 증거 해시를 포함하는 허용 목록 기반 연구 자료를 게시한다. 인증 파일·provider 세션 ID·명령행·환경변수·로컬 절대 경로·원시 진단 로그는 게시 대상에서 제외한다. 공개본은 원시 native 증거 전체와 같지 않으므로 로컬 지속 저장소도 보존해야 한다.

## 상태 해석

작업판의 `open`은 미선점, 모델 담당자 표시는 소유권 예약이다. 실제 대화 수는 작업 완료 보고 시 확정되며, 실행 중인 묶음은 잠시 미보고로 남는다. 기술 점검 진행률은 각 환경의 `calibration` 아래 기록에서 확인한다. `complete`, `partial_failed`, `blocked`를 구분하며 중단 상태를 완료로 표시하지 않는다.
