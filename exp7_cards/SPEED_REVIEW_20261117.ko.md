## 우선 적용할 개선안

1. **연속 공급.** 각 대화는 기존처럼 자기 CLI 세션에서 10라운드·34턴을
   순서대로 진행하고, 종료된 슬롯에만 사전 배정된 새로운 독립 대화를 넣는다.
   세션을 다른 시행에 재사용하거나 34턴을 묶어 질문하지 않는다. 원래 7개
   모델 × 3수준 × obj/seq의 표본 배정과 조기 중단 기록을 보존한다.
2. **전송과 기록을 분리.** 이미 개선한 실제 전송 직전 pacing과 현황판 쓰기
   직렬화를 새 본수집 프로파일에 연결한다. 현황판 Git 업로드가 모든 모델
   전송을 직렬화하지 않게 하되, 결과 기록·중단 상태 확인·원본 보존은 유지한다.
   현재 가속 어댑터는 기술 시험에 사용됐지만 기존 본수집 worker에 아직
   연결되지 않았다.
3. **429를 실제 오류와 native 로그 양쪽에서 감지.** 응답 이벤트의 HTTP
   상태와 native retry 로그를 별도로 집계한다. 429가 나면 새로운 전송을
   멈추고, 진행 중인 요청은 확인 가능한 최종 상태를 보존한다. 전송 여부가
   불확실한 요청은 자동 재전송하지 않는다. 다시 시작하는 속도나 제외·대체
   시행은 별도로 기록하고 검증한다.
4. **소규모 재측정 후 증속.** 별도 기술 시행에서 연속 공급, 100회/분,
   14개 동시 대화를 먼저 10~15분 검증한다. 실제 완료율이 상한보다 충분히
   낮을 때만 동시성을 올리는 비교를 한다. 요청 상한 증가는 검증된 단계와
   429·모델별 실패를 보고 작은 간격으로 판단한다. 한 번의 429나 무오류
   시험만으로 최고 한도를 단정하지 않는다.

같은 285,600턴을 계산상 85.3회/분으로 처리하면 약 55.8시간, 96.5회/분으로
처리하면 약 49.3시간이다. 후자는 지난 시험의 첫 4분을 외삽한 **가상
시나리오**이며, 연속 공급 테스트·세션 초기화·장시간 제한·결과 저장·재시작
비용을 반영한 실측 완료 시간이 아니다. 시간 절감 가능성은 약 6.5시간이다.

실제 본수집은 현재 STOP이고, 구 실행에서 완료 0개·중단 6개를 보존한 상태다.
새 운영 프로파일, 별도 기술 검증, 중단 시행 조정 및 저장·현황판 점검 없이
가속 연구 수집이 진행되고 있다고 해석하면 안 된다.
