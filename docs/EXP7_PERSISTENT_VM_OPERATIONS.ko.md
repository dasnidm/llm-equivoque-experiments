# 실험 7 persistent 기술점검 VM 운영

새 소스 브랜치 `experiment/exp7-persistent-2026-11-08`의 freeze와 원본 코드 해시를 확인한다. 공통 현황판은 `exp7/persistent-v1-coordination`, 결과 접두사는 `exp7/persistent-v1-results`다. 기존 현황판과 기존 작업 디렉터리를 사용하지 않는다. 최초 운영 정책은 모델별 예약 1이다. 최초 보드의 전체 예약 한도 8은 서비스 용량을 의미하지 않는다. Astra의 첫 34턴 점검 후 두 VM의 부하를 측정하기 위해 2026-11-08 UTC에 공통 보드 한도를 8에서 2로 낮췄다. 현황판은 전체 한도를 강제하지만 모델별 1 제한은 운영 정책이다. 한 VM의 요청 간격 1초는 계정 전체 요청 제한이 아니다. 다른 VM의 시작 시점과 동시 요청 증가는 실제 지연·오류를 보고 조정한다.

모델마다 별도 VM 작업 디렉터리에서 `prepare`를 1회만 실행하고, 같은 VM이 해당 모델의 소유권과 결과를 유지한다. 기존 소유권을 임의로 빼앗지 않는다. 공통 보드가 허용하는 다른 VM의 기술점검은 진행할 수 있다. 중복 기술점검과 본실험 진입을 막기 위해 각 VM은 `prepare`만 수행하고 본실험 자동 실행을 대기한다. 작업 배정은 현황판의 모델 소유권과 토큰으로 확인한다. `prepare`에 지정한 `--concurrency`는 현황판 예약과 실제 pool에 똑같이 적용된다. 예약을 변경하려면 먼저 정지하고 변경 시점·사유를 기록한다. 새 STOP은 자동 해제하지 않는다.

기술점검은 모델당 18개 새 대화, 최대 612턴이다. 완료되면 `exp7_main_v2.worker.verify_readiness`가 각 대화의 34턴, 실제 RPC, 동일 프로세스·대화, 프롬프트·스키마, 도구 사용 여부 및 과학 프로토콜을 검증한다. 실패·불확실 요청의 원본은 보존하고 자동 재시도하거나 대체하지 않는다. `python -m scripts.exp7_persistent_calibration_backup --work-dir <VM별 작업 디렉터리>`는 중지된 기술점검의 원본을 비공개 저장소 `raw/<새 실행 ID>/<모델>` 브랜치에 별도로 압축해 업로드하고 원격 해시를 읽어 확인한다. 이 도구는 원본을 삭제하지 않는다.

각 모델의 별도 기술점검, 원본 감사, 비공개 백업, 성공 턴/분·실제 요청 중첩·p95 지연 및 모델 목록 조회와 응답 요청의 429 분류를 확인하기 전에는 본실험을 시작하지 않는다. 어느 한 VM의 점검 결과가 모든 모델의 점검 결과를 대체하지 않는다. `exp7_ops_v1.measure`의 요청 중첩은 로컬 체크포인트 시간 구간이며 실제 서버 내부 동시 실행 수를 직접 관측한 것은 아니다. 공통 전체 부하는 여러 VM의 시간 구간을 결합해 판단한다.
