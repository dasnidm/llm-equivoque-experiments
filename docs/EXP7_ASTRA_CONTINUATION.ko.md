# Astra 중단 보존 및 10병렬 재개 기록

**후속 상태:** 실제 10병렬 시도 `c10-01`과 catalog 설정 적용 시도 `c10-02`가 모두 모델 목록 갱신 429로 중단됐다. 오프라인 설정 검증만으로 실제 실행 경로의 조회가 제거됐다고 볼 수 없다. 다음 조치는 기존에 검증된 원래 CLI의 **3병렬로 복귀**하는 것이며, 아직 10병렬 통과를 주장하지 않는다. 아래 경과와 계획을 시간순 근거로 보존한다.

2026-11-07. 사용자의 “계속해” 지시에 따라 현재 VM의 10병렬 기술 검증과 본실험 재개를 진행한다. 이 문서는 실행 전 복구 계획이며, 검증 성공이나 재개 완료를 뜻하지 않는다.

## 현재 근거

- 본실험 83개 대화 완료, 3개 중단, 현재 배치에서 4개 미시작. 기존 2,863개 호출 예약 중 실제 응답 2,860개가 기록되어 있다.
- 이 VM의 Astra 단일 인증 확인 호출은 성공했다. 별도 운영 점검 1회이며 본실험·기술 검증 데이터에 포함하지 않는다. 다른 VM의 인증 상태는 확인되지 않았다.
- 중단된 세 대화와 기존 공개 결과는 그대로 보존한다. 기존 배치의 상태·저널·원시 디렉터리·823개 예산 티켓을 대조해 네 배정이 한 번도 시작되지 않았음을 확인했다.
- 기존 배치 원본은 비공개 로그 레포에 별도 중단 시점 스냅샷으로 검증·백업했다.

## 실행 순서

1. 원본 파일 해시를 묶은 복구 계획과 세 중단 상태의 보존 확인서를 만든다.
2. 현황판의 중단 사유·시각·실험 식별자·각 VM 예약 상태가 검토 당시와 같은 경우에만, 사용자 지시에 따른 공유 중단 해제를 한 번 기록한다. 공유 해제는 다른 VM에도 적용된다. 새로운 중단 신호는 자동 해제하지 않는다.
3. 종료된 이전 실행기의 잠금과 보존 확인서를 검사한 후 이 VM을 10병렬로 설정한다.
4. 새 기술 검증 `c10-01`에서 별도 대화 18개·612호출, 오류 여부와 실제 요청 시간 구간의 최대 동시성 10을 확인한다.
5. 통과하면 배치 `model-04-job-0003`의 미시작 배정 `main-030537`, `main-029898`, `main-038103`, `main-035551`만 최대 3병렬로 실행한다. 추가 호출은 최대 136회이며 원래 배치 예산 1,020회 이내다.
6. 기존 공개 결과를 덮어쓰지 않고 별도 revision을 게시한다. 네 대화가 모두 성공하면 해당 배치는 27 완료·3 중단·0 미시작, 총 959개 호출 예약으로 종료한다.
7. 미래 배치에 걸어 둔 운영용 보류만 해제한 뒤 본실험을 10병렬로 재개한다. 중단된 세 대화의 재시도·대체 표본 추가는 하지 않는다.

`exp7_ops_v1/recovery.py`와 명시적 보존 확인서를 받는 운영 도구만 추가했다. 사전 동결된 실험 코드, 배정, 프롬프트, 호출 상한은 변경하지 않았다. 복구·동시성 조정·측정·스냅샷 테스트 42개 및 동결 파일 검증을 통과했다.

## 실제 10병렬 점검 결과: CLI 모델 목록 조회 429

14:29:54 UTC에 `c10-01`을 시작해 실제 로컬 요청 동시성 10을 관측했다. 모델 답변 100개는 모두 정상 반환됐지만, 그중 여섯 호출의 CLI stderr에 모델 목록 갱신 HTTP 429가 남았다. 구성요소는 `codex_models_manager::manager`, 오류는 `failed to refresh available models ... 429 Too Many Requests`다. 인증 오류는 관측되지 않았다.

동결된 중단 감지기는 이 진단을 감지해 공통 STOP을 설정했다. 첫 STOP은 14:30:59, 반복 기록의 마지막 시각은 14:31:12다. 다음 열 요청은 예산 예약 후 native 실행 전에 차단됐으며, 기존 답변을 재호출하지 않았다.

- 검증 대화: 18개 예정, 10개 시작·중단, 8개 미시작, 완주 0개.
- 호출: 예약 110, 정상 응답 100, 다음 요청의 전송 전 차단 10.
- 기술 검증은 통과하지 않았다. 답변 100개 성공만으로 10병렬 지속 안정성을 주장하지 않는다.
- 본실험은 여전히 83완료·3중단·현재 배치 4미시작이다. 위 계획의 미시작 네 대화 실행이나 미래 작업 보류 해제를 수행하지 않았다.
- 원인·집계는 [별도 기계 판독 기록](data/exp7-astra-c10-2026-11-07/attempt-c10-01.json)에 저장했다.

CLI가 매 턴 새 프로세스로 시작하며 공유 모델 캐시가 존재해도 모델 목록 조회를 수행하는 상황이다. `--ignore-user-config` 때문에 일반 사용자 설정 파일 변경만으로는 적용되지 않는다. 실험 프롬프트·모델·추론수준을 유지하면서 모델 목록만 정확히 고정할 수 있는 지원 설정을 조사 중이다. 오류를 무시하거나 중단된 검증을 이어서 완주한 것으로 취급하지 않는다.

## 모델 목록 고정 설정 검증과 새 점검

운영 설정 `catalog-profile-02`를 별도로 준비했다. 설치된 CLI의 지원 옵션 `model_catalog_json`에 현재 캐시의 모델 10개를 그대로 넣는다. 실험 자식 프로세스에만 실행 래퍼를 적용하며, 원래 인자에 catalog 옵션 하나만 추가한다. 기존 프롬프트·스키마·모델·추론수준·CLI 버전·429 중단 감지기는 그대로다. CLI 바이너리, 모델 목록, 래퍼와 운영 코드의 해시를 기록하고 변경 시 실행을 차단한다.

실제 CLI의 점검 출력은 원본의 모든 필드와 일치했다. CLI가 추가 출력하는 `base_instructions` 필드는 기존 `instructions_template`의 정확한 복사본임을 10개 모두 확인했다. 이 직렬화 차이를 처리하기 전의 `catalog-profile-01`도 보존했으며 적용하지 않았다. 별도 검사에서 `--ignore-user-config`에도 명시적 catalog 옵션이 적용됨을 확인했다. 점검 프로세스와 자식의 네트워크 syscall 추적에서는 Internet socket과 connect가 각각 0회였다. 이 과정의 모델 생성 호출은 0회다.

근거: [고정 모델 정보와 바이너리 해시](data/exp7-astra-c10-2026-11-07/catalog-profile-02.json), [정확한 CLI 버전의 catalog 로더](https://github.com/openai/codex/blob/rust-v0.159.0-alpha.3/codex-rs/core/src/config/mod.rs#L4056), [static model manager](https://github.com/openai/codex/blob/rust-v0.159.0-alpha.3/codex-rs/models-manager/src/manager.rs#L647), [추가 출력 필드의 정의](https://github.com/openai/codex/blob/rust-v0.159.0-alpha.3/codex-rs/protocol/src/openai_models.rs#L864).

이 검증 후 원격 현황을 다시 확인해 운영자가 한 번 재개하며, 별도 `c10-02`에서 새 대화 18개·612호출을 검사한다. 중단된 `c10-01`을 재실행하거나 그 100개 응답과 합쳐 통과시키지 않는다. 새 검증 통과 후에만 위 미시작 네 배정의 계속 실행과 본실험 10병렬 재개를 진행한다.

## c10-02 실제 결과와 3병렬 복귀 결정

14:50:11–14:51:35 UTC의 실제 검증에서도 100개 생성 응답은 성공했지만, 이번에는 8개 native stderr에 모델 목록 갱신 429가 관측됐다. wrapper의 실제 실행 100개와 원래·추가 인자의 해시를 모두 대조해 설정이 인자에 추가됐다는 점은 확인했다. 그러나 전체 실행 경로에서 모델 목록 재조회를 제거했다는 주장은 실제 관측과 맞지 않는다. 정확한 CLI 내부 경로는 아직 해결되지 않았다.

두 번째 시도도 10개 중단·8개 미시작, 110개 예약·100개 정상 응답·전송 전 차단 10개이며, readiness는 생성되지 않았다. 두 시도를 합쳐 기술 검증을 통과시키거나 본실험으로 포함하지 않는다. HTTP 403 재연결 진단도 38개 파일에서 관측됐으며, 생성 응답 성공과 별도로 원본에 보존했다. 인증 401은 관측되지 않았다.

사용자의 계속 진행 요청에 따라, 추가 10병렬 시험 대신 기존에 정상 운영한 **원래 CLI·3병렬·기존 기술 검증 attempt-01**로 돌아가는 복구를 준비한다. 이 변경은 목표 동시성 10을 검증했다는 의미가 아니다. 미래 작업에 걸어 둔 운영 보류는 3병렬 복귀와 미시작 네 배정의 처리 확인 후에만 해제한다. 본실험 3개와 두 기술 검증의 20개 중단 기록은 원본·체크포인트를 그대로 보존한다. 다른 VM의 소유권과 전체 예약 상한 30은 변경하지 않는다.

## 3병렬 복귀 및 계속 실행 완료

사용자가 다시 명시적으로 STOP 해제와 3병렬 계속 실행을 요청했다. 15:01 UTC에 이 VM의 예약과 로컬 설정을 3으로 복귀시키고 공유 STOP을 해제했다. 기존 정상 기술 검증의 18개 대화·612호출·관측 동시성 3, 두 실패 검증의 보관본과 현재 파일, 원래 중단 기록 세 개를 확인했다. 원래 CLI를 사용하며 catalog wrapper는 적용하지 않았다.

기존 미시작 네 배정만 실행해 15:07:57에 모두 정상 완료했다. 3번 작업은 **27완료·3중단·0미시작**, 호출 예약 959회로 종료했다. 원래 공개 결과와 기존 상태는 그대로 남기고 별도 결과 revision을 추가했다. 이 VM의 본실험 누적은 **87완료·3중단**, 정상 응답 2,996개·호출 예약 2,999개다.

새 원시 자료와 복구 영수증 3,409개 파일을 비삭제 스냅샷으로 검증하고 비공개 로그 레포에 게시·원격 해시 확인을 마쳤다. 기존 중단 시점 스냅샷도 보존했다. 15:08:57에 미래 작업의 운영 보류를 정확히 원상복구하고, 15:09:07에 원래 CLI·3병렬·기술 검증 attempt-01로 본실험 실행기를 다시 시작했다. 이후 작업을 순서대로 가져오며 기존 백업 sidecar도 계속 동작한다.
