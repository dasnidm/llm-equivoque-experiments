# 재시도 포함 실효 처리량 비교 사전 기록

2026-11-08 사용자 요청: “이거까지 감안해서 더 효율적인 방안 찾고 테스트해.
그리고 현재 실행전략 수정하는게 이득이면 수정해”.

기존 본실험 STOP, CLI 업그레이드 점검 HALT, 헤더 진단 STOP은 그대로 둔다.
새 실행 범위는 `equivoque-2026-11-08-exp7-retry-efficiency-v1`이며
`/workspace/work/exp7-retry-efficiency-20261108-v1` 아래에 별도 저장한다.
본실험 표본은 0이고, 실패·미확정 시행을 재실행하거나 대체하지 않는다.

## 바뀌는 판단 기준

429 경고 0건만으로 운영 후보를 고르지 않는다. 고정된 재시도 정책하에
전체 배정의 완료율, 대기 시간을 포함한 성공 턴/분, p95 지연, 실제 HTTP
시도 수, 중복 질문·도구 사용·미확정 완료 여부를 함께 평가한다.
이전 점검의 원본·기존 판정은 보존하고 별도 파생 비교를 추가한다.

## 재시도 규칙

- 기존 native 인증과 고정된 공식 Codex 엔드포인트, 프록시·CA·TLS 검증을 유지한다.
- CLI 0.167.0, 한 대화에 하나의 persistent app-server/thread.
  native request/stream 재시도는 모두 0으로 고정한다.
- HTTP/SSE 중계기가 **완결된 HTTP 429**의
  `error.type=rate_limit_error`, `error.code=turn_rate_limit_exceeded`만 재시도한다.
  원본 요청 바이트를 메모리에 유지해 똑같이 전송하며 CLI `turn/start`는 추가하지 않는다.
- `Retry-After` 또는 `Retry-After-ms`를 지키고, 없으면 지수 대기를 적용한다.
  0.1~0.4초의 결정적 jitter를 더한다. 모든 pool 작업이 하나의 대기 시각과
  요청 시작 간격을 공유하며, 재시도도 물리 요청 예산에 포함한다.
- 한 논리 요청은 최대 재시도 4회, 대기 포함 240초까지 허용한다.
  한 stage는 물리 시도 600회로 제한하고, 900초가 지나면 새 전송을 차단한다.
  이미 진행 중인 요청은 지정된 timeout 아래에서 종료 상태를 보존한다.
- HTTP 200 이후 오류·연결 단절·시간 초과·401/403·주간 quota 오류·알 수 없는 오류는
  자동 재시도하지 않는다. 새 STOP을 남기고 미확정 상태를 보존한다.
- HTTP 429가 모델 실행 전 거절이라는 운영 해석에 한정한다. 공급자 내부의
  실행 횟수를 완전히 증명하거나, 실패한 모델 응답을 새 응답으로 대체하는 방식이 아니다.

## 비교

각 설정은 Astra와 5.6 Sol medium, cards/seq/en_schema 조건에서 **새 대화 12개
(모델당 6개) × 원래 34턴 = 408개의 논리 턴**을 수행한다. 동일한 두 frozen
시작 설정과 프롬프트·스키마·순서를 공통 사용하고, 대화·응답을 이어받지 않는다.

| 순서 | pool | 물리 요청 시작 상한 | 역할 |
| --- | ---: | ---: | --- |
| 1 | 6 | 분당 100 | 현재 보수적 운영 후보를 새 경로에서 재측정 |
| 2 | 8 | 분당 110 | 이전 native 재시도 포함 약 98턴/분 후보 |
| 3 | 10 | 분당 160 | 더 큰 pool과 공통 cooldown의 실효 이득 확인 |

pool과 시작 상한을 묶은 **운영 전략 비교**이며 순수한 pool 효과의 실험은 아니다.
설정 사이에는 최소 65초의 무호출 구간과 남아 있는 서버 대기를 지킨다.
이것이 계정의 모든 버킷을 리셋한다는 뜻은 아니다. 같은 계정의 외부 사용과
서버 시간 변동을 완전히 통제하지 못하는 순차적·탐색적 점검이다.

세 설정 모두 34턴과 원본 RPC/과학 프로토콜 감사가 통과해야 한다.
재시도 요청의 바이트 동일성과 모든 작업의 cooldown 준수도 별도로 감사한다.
새 프로필은 HTTP/SSE이므로 기존 WebSocket 결과와 응답 분포 동등성을 주장하지 않는다.

408턴은 장기 처리량의 정밀 추정치가 아니다. baseline 대비 5% 이상 빠른
완결·감사 통과 후보가 있으면 그중 가장 빠른 설정으로 동일한 12개 새 대화를
한 번 더 실행한다. 확인 실행도 baseline보다 5% 이상 빠를 때 운영 권장값을
변경한다. 차이가 작으면 더 낮은 pool·적은 재시도를 선호한다.
범위를 넘는 추가 부하나 미확정 시행의 대체를 자동으로 하지 않는다.

최대 계획은 최초 비교 1,224 성공 턴, 필요시 확인 408턴이다. 모든 원본과 실패,
request ID·대기·시도 기록을 보존하고 비공개 GitHub 저장소에 해시 검증 백업한다.
현재 VM 한 대의 공유 pool을 측정하며, 여러 물리 VM에서 같은 성능이라고 주장하지 않는다.
여러 VM은 물리 요청 예산을 합산해야 한다. 각 VM에 동일한 전체 RPM을 따로 부여하지 않는다.

## 실행 전략 반영 범위

이득이 확인되면 새 권장 프로필과 VM 지침에 기록한다. 구 실행의 freeze를
고치거나 기존 readiness를 새 실행에 유효한 것으로 만들지 않는다.
새 본수집은 별도 실행 ID·동결 실행 프로필·모델별 readiness 아래에서 시작해야 한다.
이 점검은 기존 STOP을 해제하거나 구 본수집을 자동 재개하는 명령이 아니다.
