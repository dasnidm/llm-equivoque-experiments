# RPC 성공과 429 없는 부하를 구별하는 판정 정정

10:22 UTC경 별도 native SQLite 로그에서 **RPC에 노출되지 않은 response 429
재시도 경고**를 확인했다. 기존 계측기는 원본 RPC 오류와 stderr만 검사했다.
환경의 `RUST_LOG`는 `codex_exec_server=info,codex_cli=info,error`였으므로
`codex_core::responses_retry`의 WARN은 stderr에서 보이지 않았고, CLI도
첫 WebSocket 재시도를 RPC 오류로 표시하지 않을 수 있었다.

이 때문에 `summary.json`의 `response_429_records=0`은 **관측한 RPC 오류 0건**을
뜻할 뿐 실제 native 429가 없었다는 증거가 아니다. 원본 summary/RPC/결과는
수정하지 않고, 별도 SQLite 감사와 정정된 파생 판정을 추가한다.

| 점검 | 완료 대화 | RPC 429 | native 429 재시도 경고 | 새 운영 판정 |
| --- | ---: | ---: | ---: | --- |
| 안정판 2모델·6병렬·100회/분 상한 | 6/6 | 0 | 0 | 이 유한한 부하 점검 통과 |
| 안정판 8모델·8병렬·160회/분 상한 | 8/8 | 0 | 16 | 429 없는 부하로 인정하지 않음 |
| 안정판 2모델·8병렬·110회/분 상한 | 8/8 | 0 | 10 | 429 없는 부하로 인정하지 않음 |
| 안정판 8모델·10병렬·200회/분 상한 | 10/16 | 0 | 30 | 수동 중단·6 pending 보존 |

경고 건수는 HTTP 시도 수나 모델 실행 수가 아니다. `retry_429=false` 같은
설정 문자열, UUID나 수치에 포함된 429를 세지 않고, 실제 retry 경고의
`last status: 429` / `429 Too Many Requests` 문맥만 센다.

8모델 점검에서는 **8개 모델 모두** 10:13:04~08경 재시도 경고를 받았고,
계산된 재시도 예정 시각은 10:13:24~25에 모였다. 다음 묶음도 10:14:24~25로
모였다. 서로 다른 모델이 비슷한 해제 시각을 받은 것은 계정·접속 경로 등에
걸친 공통 단기 제한의 근거다. 이 로그만으로 계정, IP, Cloud 프록시 중
정확히 어느 구성요소가 제한했는지 또는 고정 RPM 수치를 확정할 수는 없다.

발견 직후 새 HALT를 기록하고 진행 중 app-server를 종료했다. 현재 10병렬
점검의 395개 성공 턴, 10개 완결 대화와 6개 pending을 모두 보존했다.
새 STOP은 해제하지 않았다. 이 자료는 전부 기술점검으로, 본실험 표본이 아니다.

처음의 RPC 성공 판정에 따라 다음 부하를 시작한 계측 누락도 기록한다.
이후 보고기는 native SQLite까지 함께 감사하며, native telemetry가 없거나
재시도 경고가 있는 stage를 429 없는 부하로 표시하지 않는다. 향후 비교
wrapper도 종료 후 같은 감사를 거치게 수정했다. 이것은 **사후 감사 강화**이며,
CLI 내부 재시도를 발생 전에 막는 기능이라고 주장하지 않는다.

향후 shim은 자식의 `RUST_LOG`에 `codex_core::responses_retry=warn`을 더해
경고가 stderr에서도 보이게 한다. 재시도 자체를 끄는 설정은 아니다.
기존의 `unbounded_connection_retries=false` 역시 **무한 재시도만 끄며,
기본 제한 횟수의 재시도를 끄는 설정은 아니다.** 공식 0.167.0 소스의
기본 stream 재시도 값은 5이다. 현재 HALT가 있으면 새 wrapper는 startup
전부터 실행을 거부한다. 기록된 STOP은 그대로 남긴다.

경고 출력 수정은 실제 CLI와 로컬 가짜 429 서버로 검증했다. 20초 Retry-After를
반환한 fixture에서 약 0.30초 안에 stderr 경고를 확인했고, 그때 RPC 오류는
0건이었다. 외부 모델 요청은 0건이며 가짜 인증과 loopback만 사용했다.

실제 수집 전에는 경고 관측과 native 재시도 정책을 새 프로필로 검증해야 한다.
재시도 자체를 명시적으로 통제하는 대안은 공식 Responses 클라이언트의
`max_retries=0`이다. 상태가 불확실한 요청을 자동 재전송하거나 실패 시행을 대체하지 않는다.
