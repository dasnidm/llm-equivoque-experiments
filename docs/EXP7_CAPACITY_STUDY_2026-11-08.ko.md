# 실험 7의 429와 처리량 점검

본실험은 공통 STOP을 유지한다. 본실험의 실패·중단 요청을 재전송하거나 교체하지 않는다. 사용자의 병렬 효율 확인 요청에 따라 별도 실행 `equivoque-2026-11-08-exp7-capacity-v1`에서 새 기술 대화만 사용한다. 기술 대화는 본실험 표본에 포함하지 않는다.

두 VM은 각각 `PersistentTransport`와 1초 간격 limiter를 가지고 있었다. limiter는 VM 또는 worker 내부에만 공유되며 두 VM의 합계 요청량을 제한하지 않는다. 예약한 10 pool과 실제 서버에 요청을 보내고 있는 턴의 수는 다르다. Astra의 응답시간 평균 약 2.44초와 worker당 1초 간격을 고려하면 10 pool은 대부분 요청 순서를 기다릴 수 있다. 429 원문은 `exceeded retry limit, last status: 429 Too Many Requests` 및 `responseTooManyFailedAttempts/httpStatusCode:429`이다. 해당 오류는 응답 요청에서 발생했으며 모델 목록 조회 429는 관측되지 않았다. RPC가 보존한 최종 오류만으로 내부 HTTP 재시도 횟수, 공급자의 요청·토큰 제한값, 계정 쿼터 원인을 확정할 수 없다.

이 기술 점검은 동일한 frozen prompt/schema, 10라운드+후속 질문 총 34턴을 사용한다. 모델은 Astra와 5.6 Sol, effort는 medium, 영어/schema, cards/seq로 고정한다. 각 시행은 새 프로세스·대화이며 반복 대화는 독립 기술 시행이다. 계정 전체 실제 turn/start 송신을 최소 1초 간격으로 묶고, pool 1·2·3·4를 단계적으로 비교한다. 각각 2·4·6·8개 대화(68·136·204·272턴)를 계획한다. 4 pool까지 처리량이 10% 이상 계속 개선되면 6 pool 12개 대화를 추가한다. 이후에도 10% 이상 개선되면 8·10 pool까지 확장하되 10을 초과하지 않는다. 단계 간 처리량 차이가 작으면 더 많은 pool을 안정성 향상으로 해석하지 않는다. 가장 효율적인 통과 설정은 필요시 재확인한다.

각 단계는 raw RPC, 실제 로컬 송신 시각, app-server 시작/완료 시각, 성공 턴/분, p95, 429 진단, 미확정 요청, 완료 대화 감사를 기록한다. 첫 429 또는 비정상 대화가 나타나면 신규 송신을 중단하고 해당 단계를 재시도하지 않는다. 실패 단계 때문에 본실험 STOP을 해제하지 않는다. 원본은 별도 작업 디렉터리와 비공개 원본 저장소에 보존한다. 한 VM에서의 공유 limiter 시험은 다중 VM 분산 limiter 구현을 검증하는 것은 아니다. 유한한 시험에서 429가 없었다고 영구적인 무오류 한도를 주장하지 않는다.

60회/분이라는 시험 상한과 공급자 한도를 혼동하지 않기 위해 기본 sweep이 모두 통과하면 추가 속도 경계를 확인할 수 있다. 두 모델의 독립 transport(각 1초 제한)를 로컬에서 만들고 실제 송신에 계정 공통 간격을 적용한다. 4 pool·0.75초 간격(상한 80회/분), 6 pool·0.6초 간격(100회/분) 순으로 측정한다. 앞 단계가 오류 없이 통과한 경우에만 뒤 단계를 시작한다. 계속 통과하면 110·120회/분까지 검토하되 120을 초과하지 않는다. 429가 나오면 경계 시험을 중단하고 마지막 통과 부하와 실패 부하를 함께 보고한다. 이 추가 측정은 같은 본실험 표본의 재시도가 아니며 새로운 독립 기술 대화다.
