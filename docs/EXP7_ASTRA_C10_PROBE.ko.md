# Astra VM의 10병렬 기술 점검

2026-11-07 사용자 요청: 현재 VM에서 대화 10개를 동시에 진행할 수 있는지 시험하고, 통과하면 적용한다. 본실험 프롬프트·배정·판독기·동결 해시는 유지한다. 운영 추가 코드는 `exp7_ops_v1`에 분리한다.

## 단위

대화 한 개는 새 세션에서 게임 10라운드와 마지막 확인 4응답을 수행하는 독립 시행이다. 각 라운드는 두 번의 선택과 한 번의 판단/ACK로 구성된다. 따라서 완주 대화 한 개는 게임 10라운드, 논리 호출 34회다. R_A의 중간 판단 생략은 ACK로 대체하므로 호출 수는 같다. 대화 10병렬은 독립 세션 10개의 진행을 겹치는 것이며, 한 세션의 라운드를 동시에 처리하지 않는다.

## 전환 절차

1. 본실험의 진행 중인 대화·요청을 종료 신호로 끊지 않는다. 아직 시작하지 않은 마지막 Astra 작업 한 개에 식별 가능한 운영 보류를 설정한다. 현재 작업의 권한·owner·token·배정은 그대로이며, 작업 완료 후 다음 작업 선점만 기존 worker가 거부한다.
2. 원래 작업 행과 운영 보류 행을 원격 변경 전에 로컬에 기록한다. 이 보류는 수집 실패가 아니며 호출·대화 결과를 만들지 않는다. 작업이 이미 시작됐거나 기존 보류가 있으면 변경을 거부한다.
3. 기존 worker가 실행 중일 때 원격의 동시 실행 자리 10개를 먼저 예약할 수 있다. 이것은 새 VM과의 예약 충돌을 막는 조치이며, 실행 중인 로컬 pool과 identity는 계속 3으로 유지한다. 전체 상한 10은 올리지 않는다. 다른 VM의 예약으로 자리가 부족하면 그 예약을 지우지 않고 전환을 거부한다.
4. 기존 worker 종료, worker 잠금 해제, 활성 요청 없음, 현재 작업의 게시·압축 완료를 확인한 뒤 같은 모델·owner·token을 유지하며 로컬 identity의 병렬 수를 10으로 맞춘다. 변경 전후와 부분 전환 복구 증거를 남긴다. 미래 작업 보류는 기술 점검 중에도 유지한다.
5. 동결 worker의 `prepare --calibration-attempt c10-01 --concurrency 10`으로 새로운 기술 대화 18개를 실행한다. 최초 3병렬의 `attempt-01` 통과 기록을 10병렬 통과로 재사용하지 않는다.
6. 기술 점검을 실제 통과한 경우에만 운영 보류 행이 저장된 행과 정확히 같은지 확인한 후 원래 미시작 상태로 복원하고, 같은 work-dir과 10병렬 설정으로 본실험 `run`을 재개한다. 실제 실패·중단 작업은 복원 대상이 아니며 이미 완료한 대화는 재호출하지 않는다. 원본 백업은 기존 독립 프로그램을 계속 사용한다.

## 점검 범위와 판정

18개 대화는 동결된 calibration 선택 함수가 정하는 low/medium/high, 게임·프레임·출력 형식 사례다. 최대 612회 호출이며 본실험 데이터와 분리한다. 실제 대화 기록·native 증거·형식 판독·동결 해시 검증을 모두 통과해야 한다. 응답의 방향이나 가설에 유리한 정도는 통과 기준에 넣지 않는다.

완료·실패·중단·미시작, 예약과 실제 응답 수, 진행 중 요청, 실제 겹친 요청 수, 전체 배치 처리량을 별도로 기록한다. 짧은 기술 시험 통과는 장기간·8개 VM·다른 모델의 용량 보장이 아니다. 3병렬 본실험과 10병렬 기술 점검은 사례·시간대·구성이 달라 동시성만의 인과적 속도 효과로 해석하지 않는다.

429가 발생하면 해당 기술 점검 원본을 보존하고 기존 worker의 새 호출 중단 규약을 따른다. 실패한 대화를 자동 재실행하지 않는다. 용량 오류만 확인된 경우, 모든 관련 프로세스가 종료된 뒤 최소 180초 대기하고 소유권·요청 원장·원격 STOP 사유를 검토하여 기존 3병렬로 복귀할 수 있다. 인증·도구·무결성 또는 원인 불명 오류는 이 복귀 규칙으로 숨기지 않는다. pending 증거를 삭제하거나 성공으로 바꾸지 않는다.

운영 결과는 별도 후속 기록에 남긴다. 이 문서는 실행 전 계획이며 점검 통과나 10병렬 본실험 가동 완료를 주장하지 않는다.
