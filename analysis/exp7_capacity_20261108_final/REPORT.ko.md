# Persistent 실험 7의 429 및 병렬 효율

본실험은 STOP을 유지했다. 아래 부하 측정은 별도 기술 실행이며 본실험에 포함하지 않는다.

시행 하나는 10라운드와 후속 질문을 합친 34턴이다. persistent는 프로세스와 대화를 재사용하지만 매 턴의 모델 추론 요청을 한 번으로 합치는 기능은 아니다. 대화가 길어지면 각 요청의 입력 context도 커진다. ThreadPool의 대화 수, 실제 진행 중인 RPC 턴, 분당 송신 수, 입력 토큰량을 별도로 관리해야 한다.

두 worker의 1초 간격 제한은 각자 적용되어 합계 요청량을 통제하지 못했다. 기존 오류는 응답 RPC의 `responseTooManyFailedAttempts/httpStatusCode:429`이고, 목록 조회 오류는 관측되지 않았다. 당시 계정 상태에는 사용량 63%가 표시됐고 소진 표시는 없었다. 이것은 순간 부하 원인을 지지하지만 원래 실패 응답의 HTTP 헤더가 없어 RPM·TPM·동시 요청·중간 게이트웨이 제한 중 하나로 확정할 수 없다.

기존 두 VM의 checkpoint 기록 합계는 최대 122회/60초였다. checkpoint는 송신 전 대기를 포함하므로 공급자에게 실제 도착한 HTTP 요청 수로 해석하지 않는다. CLI 내부 HTTP 재시도 횟수도 확인되지 않았다.

새 측정은 Astra와 5.6 Sol의 medium/영어/schema/cards/seq를 사용했다. 기본 pool 비교는 전체 turn/start 송신 간격을 1초로 공유했고, 후속 요청 속도 경계 시험은 표의 다른 간격을 사용했다. 모든 대화는 새 프로세스·대화로 시작했고 완료된 대화에 34턴 원본 감사를 수행했다.

합계 송신 상한 60회/분에서 선택된 시험상 효율 pool: 4.

선택 규칙은 429·미확정 요청이 없고 감사가 통과한 단계 중 최대 관측 처리량의 95% 이내에 드는 가장 작은 pool이다. 별도 확인 단계도 보존한다. 이 숫자는 두 모델/medium 및 시험 시점의 조건에 한정한다. 계정 공통 간격 1초 비교와 더 빠른 요청 경계 시험은 별도의 설정이다. 단계를 순서대로 수행해 시점과 캐시 상태는 무작위 통제하지 않았다. p95는 로컬 adapter 측정이며 일부 admission 대기를 포함할 수 있다. 한 VM의 공유 limiter 검증이 여러 VM 사이의 분산 제한 구현을 검증하는 것은 아니다. 영구적으로 429가 없다는 보장은 아니며, 다른 모델·effort·context 길이에서는 재평가해야 한다.

본실험의 기존 실패·중단 시행과 원본 로그는 보존했고 재전송·대체하지 않았다.

오류 없이 통과한 전체 설정 중 최고 관측 처리량의 95% 이내에 드는 가장 작은 pool은 `rpm100-p6`: pool 6, 합계 송신 간격 0.600초, 관측 83.7턴/분이다.

경계 시험의 첫 429에서 신규 송신을 중단했으므로 이후 120회/분과 혼합 조건 검증은 수행하지 않았다.

실제 로컬 turn/start admission의 최대 60초 창 횟수는 rpm80-p4: 77회, rpm100-p6: 96회, rpm110-p8: 107회였다. 이 횟수는 공급자 내부 HTTP 재시도까지 세는 값은 아니다.
