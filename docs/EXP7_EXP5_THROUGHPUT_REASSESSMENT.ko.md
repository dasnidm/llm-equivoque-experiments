# 실험 5보다 느린 이유: 측정 범위와 전송 상한 재점검

2026-11-08. 기존 기록만 다시 계산했다. 새 모델 호출, 본수집 재개, STOP 해제,
동결 프로필 변경은 하지 않았다. 원래 결과와 실패 기록도 유지한다.

최근의 약 94~97턴/분은 **한 VM에서 두 모델을 실행하고 우리가 합계
100회/분 상한을 건 기술점검**이다. 이를 두 물리 VM의 합계나 공급자의
최대 처리량으로 설명하면 잘못이다. 실제 이전 두 VM 동시 실행 구간은
합계 약 110턴/분이었다.

## 같은 단위로 비교

아래 단위는 성공한 논리 턴/분이다. 재시도까지 포함하는 물리 HTTP 요청 수,
완료 대화 수, 모델 내부 추론 수와 구별한다.

| 기록 | 실제 실행 범위 | 병렬 대화/실행 슬롯 | 우리가 설정한 전송 제한 | 성공 턴/분 |
| --- | --- | ---: | --- | ---: |
| 실험 5 전체 평가 | 83,160턴, 약 10시간 56분 | 성공 요청 구간 최대 40, 평균 34.57 | 입장 슬롯 제한; 고정 100회/분 상한 없음 | **126.73** |
| 이전 실험 7의 두 VM 동시 구간 | Astra VM + Sol VM, 93.66초 | 각 10 | 각 VM의 시작 간격 1초, 합계 약 120회/분 이하 | **110.18** |
| 최근 재시도 비교 | 한 VM, 두 모델, 30대화 × 34턴 | 6 | 공통 물리 시작 상한 100회/분 | **94.36** |
| 최근 FIFO 비교 | 한 VM, 두 모델, 30대화 × 34턴 | 10 | 공통 물리 시작 상한 100회/분 | **96.80** |

실험 5의 동시성은 클라이언트의 요청 체크포인트 구간이 겹친 수다.
서버 내부에서 동시에 추론한 수를 관측한 것은 아니다. 최근 FIFO 비교는
1,020개 RPC 완료 뒤 82ms 후 HTTP 종료 오류로 STOP이 남았다.
턴 완료율과 전체 운영 검증의 통과를 동일시하지 않는다.

## 확인된 원인

**최근 비교는 설정상 실험 5의 처리량에 도달할 수 없었다.** 실험 5의
126.73턴/분은 이번 100회/분 상한보다 높다. 한 번의 성공에 적어도 한 번의
물리 요청이 필요하고 재시도도 예산을 쓰므로, 장기적으로 127턴/분을 만들 수
없는 설정이었다. 126.73과 상한 100의 차이는 26.73이고, 상한과 관측 96.80의
차이는 3.20이다. 이는 설정의 산술적 제약이며, 상한을 풀면 서버가 127을
허용한다는 증거나 원인의 기여율 추정은 아니다.

**이전의 두 VM은 실제로 합계 속도를 올렸다.** Sol 실행이 시작되기 전
Astra의 106.31초 구간에서는 95턴이 완료되어 약 53.62턴/분이었다.
두 VM이 겹친 93.66초에는 Astra 92턴과 Sol 80턴, 합계 172턴이 완료되어
약 110.18턴/분이었다. 그 안의 예시 60초 구간
07:58:29.840253~07:59:29.840253 UTC에는 119턴이 완료됐다.
구간 선택은 사후적이며 요청의 경계 유입, 시작 효과, 이후 실패·중단이 있으므로
두 VM의 장기 안정 처리량이나 인과적인 두 배 향상으로 해석하지 않는다.

당시에는 각 VM에서 프로세스 시작과 턴 시작에 같은 1초 간격 제어기를
사용했다. 따라서 두 VM을 합쳐도 명목상 약 120회/분으로 제한됐다.
매 34턴 시행의 추가 프로세스 시작까지 같은 예산을 쓴다면 정상상태의 모델
턴 시작 상한은 대략 `120 × 34 / 35 = 116.57회/분`이다. 짧은 완료 구간의
119턴과는 측정 경계가 다르다.

**대기 시간도 클라이언트 쪽에 있었다.** 이전 Astra VM의 성공 턴은
요청 체크포인트부터 응답까지 평균 10.37초였고, 간격 제어 뒤 시작한
adapter 측정은 평균 2.45초였다. 차이 약 7.91초는 간격 제어 등을 포함한
adapter 측정 전 구간이다. Sol에서는 같은 차이가 약 9.10초였다.
이 시간을 전부 서버의 응답 지연으로 해석하면 안 된다.

한편 같은 모델·medium·cards·seq의 첫 30턴을 골라 보면, 실험 5의
adapter 평균은 Astra 17.16초, Sol 15.33초이고 최근 6병렬 비교에서는 각각
3.66초, 3.13초다. 현재의 개별 요청이 전반적으로 느려졌다는 설명은 이
기록이 뒷받침하지 않는다. 실행 방식과 측정 구간, 날짜, 모델 조건이 달라
이 차이를 서버 추론 성능 향상률로 환산할 수는 없다.

## 아직 확인하지 못한 부분과 운영 해석

실제 응답 요청에서 capacity 429가 발생한 사실은 유효하다. 더 높은 시작률의
별도 비교에서 cooldown이 필요했다. 하지만 100회/분이라는 공급자의 고정
한도, 전체 계정의 최적 병렬 수, 상한을 높였을 때의 안정 처리량은 식별하지
못했다. 실험 5와 현재는 날짜·CLI·전송 경로·모델 혼합·실패 정책도 다르다.
과거의 내부 HTTP 재시도 총수도 성공 턴 CSV만으로는 알 수 없다.

따라서 앞서 선택한 **6병렬/100회는 해당 상한 아래 비교한 잠정 운영값**이다.
"두 VM을 합쳐 6병렬이 계정의 최대 효율"이라고 결론 내릴 수 없다.
FIFO의 실모델 검증은 10병렬에서 했고, 6/FIFO 자체의 처리량을 직접 측정한
것도 아니다. 기존 수치·프로필은 보존하고 해석 범위를 여기에서 명확히 한다.

두 VM에 3개씩 배치하더라도 계정 전체 예산을 6병렬·100회/분으로 유지하면
합계 예산은 그대로다. VM 추가가 처리량을 높이는지는 실제 전체 실행 슬롯,
전송 예산, 공유 계정의 응답 제한을 함께 보아야 한다. 현재 비교만으로 VM의
CPU나 디스크가 병목이라는 증거는 없다.

실험 7의 전체 계획 호출이 실험 5의 약 31.8배라는 점은 전체 완료 시간에
영향을 준다. 분당 성공 턴이 낮아진 이유를 설명하는 수치는 아니다.

다음 처리량 비교에서는 한 VM과 두 VM의 **합계 pool·전송 예산을 같게**
둔 결과와, 합계 예산 자체를 높인 결과를 구별해야 한다. 이번 분석에서는
그 비교를 새로 실행하지 않았으며 본수집과 STOP 상태도 변경하지 않았다.
